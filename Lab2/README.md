## 2. Дослідницька частина: Python Application

Проводились дослідження на базі репозиторію `lab-03-starter-project-python`. Для забезпечення відтворюваності версії залежностей були зафіксовані (через `pip freeze`).

### 2.1 Оптимізація шарів (Layers Caching)

Було створено два Dockerfile:
1. **Неоптимізований** (`Dockerfile.non-optimized`): копіює весь код одразу, а потім викликає `pip install`.
2. **Оптимізований** (`Dockerfile.optimized`): копіює лише `requirements.txt`, встановлює залежності, і після цього копіює інший код.

Ми внесли зміну у вихідний код (додали коментар в `app.py`) і перезібрали обидва образи. 

| Метрика | Неоптимізований (перша збірка) | Оптимізований (перша збірка) | Неоптимізований (зміна коду) | Оптимізований (зміна коду) |
| :--- | :--- | :--- | :--- | :--- |
| **Час збірки** | ~14.2 с | ~14.8 с | **~14.1 с** | **~0.8 с** |
| **Розмір образу** | 1.02 ГБ | 1.02 ГБ | 1.02 ГБ | 1.02 ГБ |

**Висновки:** Розмір образів однаковий. Але час перезбірки при зміні коду оптимізованого образу становить менше 1 секунди, оскільки Docker бере шар із встановленими залежностями з кешу. Неоптимізований образ кожного разу інвалідує кеш на етапі `COPY . .`, змушуючи `pip install` качати пакети заново.

### 2.2 Менші базові образи: Debian vs Alpine

Було порівняно базові образи `python:3.13-bookworm` (на базі Debian) та `python:3.13-alpine`.

| Базовий образ | Час збірки (без кешу)* | Розмір фінального образу |
| :--- | :--- | :--- |
| `python:3.13-bookworm` | ~14.8 c | **1.02 ГБ** |
| `python:3.13-alpine` | ~12.5 c | **~65 МБ** |
*\*Час без урахування `git pull` самого фізобразу.*

**Висновки:** Alpine значно виграє у розмірі, адже він не містить багатьох стандартних системних утиліт і побудований на базі `musl libc`, а не `glibc`. 

### 2.3 Додавання "важких" залежностей (Numpy)

В проект було додано `numpy`. В `spaceship/routers/api.py` додано ендпоінт, що множить 10х10 матриці:
```python
@router.get("/matrix")
def get_matrix_product():
    a = numpy.random.rand(10, 10)
    b = numpy.random.rand(10, 10)
    return {"matrix_a": a.tolist(), "matrix_b": b.tolist(), "product": numpy.matmul(a, b).tolist()}
```

Перезібрано обидва образи (Alpine та Debian) з `numpy`:

| Базовий образ + Numpy | Час збірки | Розмір фінального образу | Причина затримки |
| :--- | :--- | :--- | :--- |
| `bookworm` (Debian) | **~18 с** | 1.09 ГБ | `pip` завантажує готові бінарні wheels (glibc) |
| `alpine` (Alpine) | **> 12 хв** | ~205 МБ | `pip` збирає пакети C та Fortran вручну з вихідних кодів (musl) |

**Висновки:** Для Python-проєктів з C-залежностями використання Alpine може викликати катастрофічні затримки збірки, оскільки `pip` не має прекомпільованих `.whl` для `musl`. Рекомендується використовувати Debian/Ubuntu slim версії замість Alpine (напр. `python:3.13-slim-bookworm`).

## 3. Дослідження: Musl (Alpine) vs glibc (Debian/Ubuntu) DNS

Було створено мережу `dns-lab` та запущено сервер `dnsmasq`, що резолвить `myservice.internal.corp`.
Виконано запити `getent hosts myservice.internal` з `ubuntu` та `alpine` із параметром `--dns-search="corp"`.

**Спостереження:**
- **Ubuntu (glibc):** Запит одразу йде на `myservice.internal.corp`, успішно отримується IP `10.0.0.50`. Логи dnsmasq показують один послідовний IPv4 (A) запит.
- **Alpine (musl):** `musl` відправляє паралельні запити для IPv4 (A) та IPv6 (AAAA). Він іноді робить запит прямо на `myservice.internal` (що видає NXDOMAIN), перед тим як перевіряти search domains (`.corp`), або паралельно може ігнорувати параметр `ndots`.
- **Логи `dnsmasq`:**
  - На Ubuntu: `query[A] myservice.internal.corp from 10.x.x.x -> 10.0.0.50`
  - На Alpine: `query[A] myservice.internal ... NXDOMAIN`, `query[AAAA] myservice.internal ... NXDOMAIN`, і лише потім йде на `.corp`.

**Висновки і наслідки:** Агресивна паралельна поведінка і особливості опрацювання `search` доменів у Alpine (`musl libc`) можуть призвести до DDoS-атак на внутрішні корпоративні DNS сервери (через спам AAAA запитами, навіть якщо IPv6 вимкнений) та до неочікуваних помилок `NXDOMAIN` для скорочених сервісних імен. В системах як Kubernetes це створює велике навантаження на `CoreDNS`.

## 4. Golang Application та Multi-stage builds

### 4.1 Стандартний/базовий образ
Зібрано базовий проект (`golang:1.21-alpine`).
- **Час збірки (кешований базовий образ):** ~6 сек.
- **Розмір:** ~310 МБ.
- **Вміст (через dive):** Присутні менеджери пакетів (`apk`), компілятор Go, вихідний код, інструменти тестування тощо. Майже 95% цього не потрібно для "продакшену".

### 4.2 Multi-stage build -> `scratch`
```dockerfile
# Builder stage
FROM golang:1.21-alpine AS builder ...
... \ RUN CGO_ENABLED=0 GOOS=linux go build -o main .
# Final
FROM scratch \ COPY --from=builder /app/main /main
```
- **Розмір:** **~7 МБ**.
- **Проблеми "в лоб" ("no such file or directory"):** Якщо бінарник був скомпільований для використання спільних бібліотек C (динамічна лінковка), `scratch` поверне помилку `no such file or directory`, оскільки в `scratch` немає взагалі нічого (навіть базових бібліотек операційної системи). Тому необхідно використовувати прапорець `CGO_ENABLED=0`, щоб виконати *статичну* лінковку.
- **Зручність:** Всередині контейнера взагалі відсутній shell (`/bin/sh`). Ми не можемо туди зайти командою `docker exec -it ... /bin/sh`. Це вкрай безпечно (неможливість RCE експлойтів), але незручно для дебагу. Відсутні CA сертифікати (SSL запити до зовнішніх API впадуть).

### 4.3 Multi-stage build -> `distroless`
Використано `gcr.io/distroless/static-debian11`.
- **Розмір:** **~24 МБ**.
- **Вміст:** Бінарник додатку + кореневі CA-сертифікати (дозволяють HTTPS запити) + базові інформаційні файли ОС (`/etc/os-release`, tzdata). Відсутній менеджер пакетів або повноцінний shell. Це золота середина між безпекою, розміром та функціональністю.

## 5. Практична частина (Node.js з Lab 1)

Практичну частину реалізовано у файлі `Lab1/docker-compose.yml` та `Lab1/app/Dockerfile`.

1. **Сервіси та Мережа:** Підняті 3 контейнери (`db`, `web`, `nginx`) в окремій Bridge мережі `lab_network`. Тільки `nginx` "світить" на хост порт `80`.
2. **Persistence:** Збереження БД забезпечує Docker volume `db_data` (монтується в `/var/lib/mysql`).
3. **Healthchecks & Dependencies:** Марію (MariaDB) може зайняти кілька секунд на холодний старт. Щоб Node.js аплікація не падала, в `docker-compose` на БД встановлено `healthcheck`. Сервіс `web` має `depends_on: db: condition: service_healthy`.
4. **Dockerfile для Node.js:** Реалізовано за допомогою двохетапного `node:20-alpine`:
   - На першому (Builder) встановлюються *всі* пакети.
   - На другому пакети встановлюються з параметром `--omit=dev` (або `npm ci --only=production`), щоб виключити зайві залежності.
   - Процес запускається від вбудованого непривілейованого `USER node`, що унеможливлює виконання процесу від користувача root.

## 6. Загальні висновки та рекомендації

- **Використання Multi-stage builds:** Є необхідним стандартом. Окреме середовище для збірки та для виконання процесу (з передачею лише артефактів) дозволяє кардинально зменшити розмір образу (як було показано із `golang`, від 310мб до 24мб).
- **Кешування шарів:** Розумне розділення етапів "копіювання артефактів пакетного менеджера" (напр. `package.json`, `requirements.txt`) та "решти коду" зменшує час локальної збірки з десятків секунд до часток секунди.
- **Обережне ставлення до Alpine:** Alpine Linux є відмінним варіантом для самодостатніх бінарників (Go, Rust), або для інтерпретаторів, які не тягнуть C-розширення (Node.js). Але для систем як Python з `numpy` чи `pandas`, `musl` змушує компілювати код із вихідників, що витрачає величезний час і робить образи на базі Debian-slim більш привабливими.
- **Управління DNS:** Розробляючи хмарні аплікації, треба враховувати відмінності бібліотеки `musl` (Alpine), оскільки паралельні DNS запити і ігнорування `search/ndots` можуть викликати непередбачувану поведінку.
